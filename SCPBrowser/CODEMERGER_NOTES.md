## Plate Color Consistency

- [2026-03-10 14:57] Plate colors are now centrally managed by PlateFilterControl as the single source of truth. Right-click any plate button to pick a color from a 30-swatch palette. Colors propagate to: (1) PeptideTicControl Explorer scatter plot via PlateColorChanged event -> UpdatePlateColors(), (2) ProteinHistogramControl and ProteinDistributionControl via MainControl.SetPlateColorMap(Dictionary<int, Color>), which both use ToScottPlotColor(plateId) lookups. Colors persist in the project DB as "PlateColors" setting (serialized as EscapedKey=RRGGBB). On project load, RestorePlateColors() feeds saved colors back to PlateFilterControl, then re-pushes to all consumers. The old hardcoded PlateColors hex string arrays in histogram/distribution controls have been removed.

## Resize Selection Bug Fix

[2026-03-13] Fixed bug where resizing the window broke checkbox filter styling (grey points reverted to colored, Selected Points tab showed all runs). ROOT CAUSE: RestoreCheckedStates replaced _checkedCellTypes/_checkedBioConditions/_checkedPlates field references with new HashSet instances, but _currentOptions in ScatterPlotControl still held references to the OLD HashSets. On resize, UpdatePlot read stale options showing all items checked. FIX: (1) RestoreCheckedStates now modifies HashSets in place (Clear+Add) instead of replacing references. (2) Added RaiseSelectionChanged centralized gate that checks _suppressSelectionEvents before firing, replacing all 4 direct SelectionChanged?.Invoke calls. (3) Added deferred SelectionChanged event in UpdatePlot with _updateGeneration staleness guard. (4) Removed duplicate deferred UpdateSelectionWithFilters from RefreshChart. (5) Fixed _checkedPlates not being cleared in ScatterPlot_SelectionChanged. LESSON: When HashSet references are shared across objects (options pattern), never replace the field; always modify in place.

## ClickOnce Deployment

[2026-10-15] Two install failures reported by users. (1) A campus firewall returned a 503 "File Transfer Blocked" page for some .dll.deploy files. The installer page was opened over https, but the deploymentProvider in SCPBrowser.application came from InstallUrl, which was http://, so every file download went over plain http where the firewall could inspect it. InstallUrl in ClickOnceProfile.pubxml is now https:// (the server has a valid Let's Encrypt certificate, and http still answers, so existing installs keep updating). (2) Smart App Control blocked Launcher.exe ("did not meet the Enterprise signing level requirements"), which ClickOnce reports as an invalid manifest. Launcher.exe is not built from this repo or from the .NET SDK. MSBuild copies it from C:\Program Files (x86)\Microsoft SDKs\ClickOnce Bootstrapper\Engine\Launcher.exe, which Visual Studio installs, and the copy shipped with VS 18 is still the unsigned 8.0.0-preview.1 build, so updating the SDK or VS does not fix it. setup.exe is unsigned too, and 56 of the 70 binaries in the 1.0.0.15 payload carry no Authenticode signature. Smart App Control accepts a binary without cloud reputation only if it is signed by a CA in the Microsoft Trusted Root Program; a self-signed certificate does not help. LESSON: Signing only Launcher.exe would move the block to the next file, so sign every PE file in the payload plus setup.exe. Leaving the manifests unsigned keeps the ClickOnce identity (publicKeyToken 0000000000000000) stable, so existing installs keep updating. Signing the manifests changes that identity and forces every user to uninstall and reinstall once. DECISION: releases will not be code-signed, so users with Smart App Control on must turn it off (or ask their IT) before installing.

## Plate Summary Distinct Counts

[2026-10-16] The Project Browser's Plate Data summary showed "Total Proteins/Peptides" as the SUM of the per-run counts, so a protein seen in 280 runs counted 280 times (SpaceProjectV3 Plate 8: 264,393 "proteins" for 2,761 distinct). FIX: ProteomicsData now keeps each run's identity lists, ProteinsPerFile and PeptidesPerFile (the sets behind ProteinCountPerFile/PeptideCountPerFile, filled by LoadParquetFileAsync, merged by LoadMultipleParquetFilesAsync, and ProteinsPerFile also by XlsxGeneMatrixParser), and CountDistinctAcrossRuns unions them. The browser reaches the loaded data through MainControl.LoadedData -> ProjectBrowser2.LoadedDataSource -> PlateBrowserControl. The strings are the parquet reader's pooled ones, so the lists cost one reference per run-identity pair. Gene matrices have no peptides, so that count shows n/a. Verified against an independent pyarrow count on SpaceProjectV3 (both plates exact) and on GroundTruth2. LESSON: the database cannot give distinct peptides (it stores only per-run counts), and its per-run counts can be STALE: raw_files.protein_count/peptide_count are written once at import, and projects imported before the 1% FDR filter keep unfiltered counts (SpaceProjectV3: 13 runs have no identification left after filtering, and the others lose a few dozen proteins each). The loaded data re-applies the filter at every project open, so counts shown next to the Explorer's must come from the loaded data, not from raw_files. parquet_imports.protein_count is also a sum of per-run counts, but nothing reads it.
