## ClickOnce Deployment

[2026-10-15] Two install failures reported by users. (1) A campus firewall returned a 503 "File Transfer Blocked" page for some .dll.deploy files. The installer page was opened over https, but the deploymentProvider in SCPBrowser.application came from InstallUrl, which was http://, so every file download went over plain http where the firewall could inspect it. InstallUrl in ClickOnceProfile.pubxml is now https:// (the server has a valid Let's Encrypt certificate, and http still answers, so existing installs keep updating). (2) Smart App Control blocked Launcher.exe ("did not meet the Enterprise signing level requirements"), which ClickOnce reports as an invalid manifest. Launcher.exe is not built from this repo or from the .NET SDK. MSBuild copies it from C:\Program Files (x86)\Microsoft SDKs\ClickOnce Bootstrapper\Engine\Launcher.exe, which Visual Studio installs, and the copy shipped with VS 18 is still the unsigned 8.0.0-preview.1 build, so updating the SDK or VS does not fix it. setup.exe is unsigned too, and 56 of the 70 binaries in the 1.0.0.15 payload carry no Authenticode signature. Smart App Control accepts a binary without cloud reputation only if it is signed by a CA in the Microsoft Trusted Root Program; a self-signed certificate does not help. LESSON: Signing only Launcher.exe would move the block to the next file, so sign every PE file in the payload plus setup.exe. Leaving the manifests unsigned keeps the ClickOnce identity (publicKeyToken 0000000000000000) stable, so existing installs keep updating. Signing the manifests changes that identity and forces every user to uninstall and reinstall once. DECISION: releases will not be code-signed, so users with Smart App Control on must turn it off (or ask their IT) before installing.

## Plate Summary Distinct Counts

[2026-10-16] The Project Browser's Plate Data summary showed "Total Proteins/Peptides" as the SUM of the per-run counts, so a protein seen in 280 runs counted 280 times (SpaceProjectV3 Plate 8: 264,393 "proteins" for 2,761 distinct). FIX: ProteomicsData now keeps each run's identity lists, ProteinsPerFile and PeptidesPerFile (the sets behind ProteinCountPerFile/PeptideCountPerFile, filled by LoadParquetFileAsync, merged by LoadMultipleParquetFilesAsync, and ProteinsPerFile also by XlsxGeneMatrixParser), and CountDistinctAcrossRuns unions them. The browser reaches the loaded data through MainControl.LoadedData -> ProjectBrowser2.LoadedDataSource -> PlateBrowserControl. The strings are the parquet reader's pooled ones, so the lists cost one reference per run-identity pair. Gene matrices have no peptides, so that count shows n/a. Verified against an independent pyarrow count on SpaceProjectV3 (both plates exact) and on GroundTruth2. LESSON: the database cannot give distinct peptides (it stores only per-run counts), and its per-run counts can be STALE: raw_files.protein_count/peptide_count are written once at import, and projects imported before the 1% FDR filter keep unfiltered counts (SpaceProjectV3: 13 runs have no identification left after filtering, and the others lose a few dozen proteins each). The loaded data re-applies the filter at every project open, so counts shown next to the Explorer's must come from the loaded data, not from raw_files. parquet_imports.protein_count is also a sum of per-run counts, but nothing reads it. FOLLOW-UP (same day): the first version showed n/a in the app because MainControl.LoadedData returned _currentData, which UpdateChart replaces after every filter pass with DataFilterService's filtered copy (no per-run lists, and unselected plates dropped). LoadedData now returns the object the load produced (_loadedData). The earlier check called the counting code directly and missed this, so it is now verified inside the running app: a DOTNET_STARTUP_HOOKS assembly opens a project copy through MainWindow.OpenProjectAsync, opens the Project Browser through its menu handler, selects each plate, and reads the summary controls. ## Crash Dialog at Shutdown

[2026-10-16] Closing the deployed app showed "SCP Browser - Fatal Error: DllNotFoundException: Unable to load DLL 'vcruntime140_cor3.dll'" with a stack in ModuleUninitializer.SingletonDomainUnload / _app_exit_callback. ROOT CAUSE: not our code. A Visual Studio update removed WindowsDesktop runtime 10.0.12 and installed 10.0.13 while SCPBrowser was running on 10.0.12, so at exit WPF's C++/CLI cleanup (DirectWriteForwarder) could not find vcruntime140_cor3.dll in the deleted runtime folder (the known runtime-replaced-while-running issue, dotnet/wpf#7332). Restarting the app is the remedy. FIX: App.OnAppDomainUnhandledException now only logs, with no dialog, once the app is shutting down (App.OnExit sets a flag; the dispatcher's HasShutdownStarted is checked too), because no window or data is left to lose by then. Exceptions while the app is running still get the fatal dialog. Tested before/after by launching the built exe with a DOTNET_STARTUP_HOOKS assembly that throws from a ProcessExit handler (on the exiting thread and on a separate thread) and on a background thread while the app is open: the old build showed the dialog in all three cases, and the new one only in the last. LESSON: the error log label says where an entry came from ("background thread during shutdown (no dialog shown)"), so read it before chasing a shutdown-only crash in our own code.

## Identification Box Plots

[2026-10-16] The Project Browser's Plate Data and Conditions tabs now show identifications per run as a box plot, every run a dot, above the raw-file grid and the blast-radius stats respectively (resizable with a horizontal GridSplitter). IdentificationBoxPlot (Controls/IdentificationBoxPlot.cs) draws with a DrawingContext, so the same Draw method serves the screen and every saved file. SAVING: a Save button in the plot's toolbar and the right-click menu open the same menu (Save as PNG 300 DPI, PNG 600 DPI, SVG; Copy image at 300 DPI; Copy values as TSV). A saved figure is the plot's width and at least 420 (up to 560) units tall (ExportSize), with the layout recomputed for that size, so a plot squeezed by the splitter still saves as a proper figure; it has no hover label and no muting of unselected categories. SVG comes from DrawingSvgWriter, which walks the DrawingGroup the same Draw call records (groups with transform/opacity/clip, solid-color geometries, text as glyph outlines), so it matches the PNG exactly, needs no font on the reader's machine, and its text is not editable as text. Jitter is deterministic: runs ranked by value and spread with the golden-ratio sequence, scaled by a Gaussian KDE for boxes of 15+ runs (a sina plot). Boxes of more than 40 runs draw outline, whiskers and median over the dots on a thin halo, or the dots bury them. DATA: values come from MainControl.LoadedData (ProteinCountPerFile / PeptideCountPerFile), never raw_files.protein_count (stale for projects imported before the FDR filter). A database run absent from the loaded data is plotted at 0 and counted in n when other runs of its import are loaded (no identification passed the filters: 13 runs in SpaceProjectV3), and left out when its whole import is not loaded (file missing); the caption states both counts. Manually excluded runs (excluded_runs) are drawn as grey rings and left out of the box and n, mirroring the protein histogram (shown greyed) and the analysis (excluded). Values were checked against an independent pyarrow count (Q.Value and PG.Q.Value <= 0.01, distinct Protein.Group per Run) on a copy of SpaceProjectV3: n, median, quartiles and whisker ends of all eight boxes (two plates for both metrics, four conditions) are exact, read from the running app by an in-process startup hook (DOTNET_STARTUP_HOOKS) that opens the copy through MainWindow.OpenProjectAsync, opens the Project Browser through its menu handler, and saves through the real menu items and the real Save dialog. COLORS: plates use PlateFilterControl's colors (single source, via ProjectBrowser2.PlateColorSource), with PlotColors.Ink deepening a color lighter than the reference figure's (relative luminance > 0.30) to the same hue, because the default pastel plate colors vanish as 7 px dots on the off-white card. ## Negative Controls (Background Removal)

[2026-10-19] Conditions tab: a condition can be marked "Negative control (blanks)" (several may be), its blank runs can be left out of the background estimate (checklist, or click the dot; left-out blanks are hollow rings that stay in the box), and background removal is previewed live and applied with "Apply and reprocess". Rules: frequency (a protein found in >= X% of the selected blanks, default 50%, is removed from every run the blanks apply to) and intensity (off by default; a measurement below k x the blank level, max by default or median, over the selected blanks that detect the protein, default k = 3, is removed); frequency first, then intensity on what is left. Scope per plate (default; a plate without a selected blank uses all of them) or whole project. Blank runs are left out of the cell analyses by default (checkbox). Settings: one JSON value under project_settings "negctrl.Settings" (NegativeControlSettings, invariant numbers). Design points: (1) MainControl.CompleteLoadAsync builds the analysis data from the loaded data (BackgroundRemovalService.Apply) before UpdateChart, GO enrichment and DataLoaded, so every filter stage and view inherits it; MainControl.LoadedData stays as loaded (the Conditions/Plate box plots and their Raw view read it), and with no negative control the analysis data IS the loaded object, so nothing changes for projects without one. (2) Removing a protein from a run also removes the peptides seen only under it: the loader now keeps a peptide -> protein-groups map per report file (PeptideProteinGroupsPerFile; zero sequences with two groups in Isabele's or SpaceProjectV3's reports), and TIC drops by the removed proteins' summed quantity. (3) Apply re-runs CompleteLoadAsync from memory (MainControl.ReapplyNegativeControlsAsync under MainWindow.RunProjectLoadAsync, the same hold as a load); the next profile classification is forced to recompute, because stored predictions are reused whenever the run count matches. (4) Marker-only classification reads per-cell intensities from protein_quant_summary, not the loaded data, so it is handed the applied result (BackgroundRemovalResult.Keeps) to skip removed pairs and left-out blanks. The protein coverage viewer re-reads the parquet and is not filtered. VERIFIED: loader dump (every field, enumeration order) byte-identical old vs new build on Isabele's project and SpaceProjectV3 (33 MB, same SHA-256); five settings (project/plate scope, 25/50%, intensity 3 x max/median, blanks kept or left out) give per-run protein and peptide sets, counts, TIC and every matrix value identical to an independent pandas recomputation from the parquet and the database; preview (Summarize) equals the applied copy in all five; the real ConditionsBrowserControl driven offscreen reproduces the same numbers. Isabele's data (4 clean blanks, whole project, 50%): 136 proteins removed, 1,763 of 10,360 cell measurements.

[2026-10-19, review follow-up] An independent review (with its own pandas recomputation) led to: (1) per-plate scope now needs MinBlanksPerScope selected blanks of a plate's own (default 2), else the plate uses all selected blanks: with one blank any percentage means "found in that blank" (Isabele's iPSC plate lost all 166 proteins of its single clean blank, 60 of them absent from the other plate's clean blanks); (2) blanks excluded by hand in the Explorer (excluded_runs) never estimate the background; (3) optional RequireBothRules: with both rules on, a frequent protein is removed only where the run is below k x its blank level (keeps lysate signal 16x above the blanks; Isabele, whole project 50%, k 2: 1,158 measurements instead of 1,763, 4 proteins lost everywhere instead of 136); (4) IntensityFactor default 2 (k 1 to 3 draw nearly the same line on her biopsies, whose background proteins sit at about blank level); (5) the reclassify-after-change flag is also stored in the project (negctrl.ReclassifyPending) so closing before a classification ran cannot serve old stored predictions; (6) HeadlessEmbed applies the negative controls, so headless figures match the app; (7) UI: tabs shown with no condition selected, number boxes debounced (0.1 s per preview rebuild at 470 runs) and Apply disabled while one is invalid, the checklist updated in place, blanks kept at their loaded value in the After view, closing the Project Browser with an unapplied change asks Apply / Discard / Cancel. Known approximations, zero cases in Isabele's and SpaceProjectV3's reports: the peptide map holds every group a sequence was seen under anywhere in its report file, so a peptide seen only under a removed group in one run is kept there if another of its groups is kept in that run; and the TIC drop sums protein rows, so a peptide shared by two removed groups would be subtracted twice. VERIFIED: 11 settings (floor 1 and 2, 25/50/75%, intensity either/both, max/median, Explorer exclusions, blanks kept) identical to the pandas recomputation; the reviewer's table reproduced to the measurement.
